## Overview

This page is the technical reference for integrating the Arcube widget. It covers rendering the widget, configuration, secure authentication, the event contract, both payment models, styling, and error handling.

The sequence below shows the full passenger journey end to end - from establishing the booking context, through secure token vending and widget rendering, to ancillary selection and checkout. Checkout is shown for both integration models: **Model A**, where the passenger pays inside the widget frame (Arcube is Merchant of Record), and **Model B**, where the airline captures payment on its own PSP and creates the order with `externalPSP` proof (airline is Merchant of Record).

## Prerequisites

Before integrating, make sure you have:

- **Tenant ID** - your Arcube tenant identifier.
- **Environment URL** - your assigned Arcube base URL (for example `https://api.arcube.com`), referred to below as `${arcube-url}`.
- **Widget script URL** and **widget URL** - provided by Arcube.
- **Signing secret** - held only on your secure server or edge layer, never in the browser (see [Authentication](#authentication-and-token-flow)).
- **Theme file** (optional) - a hosted JSON file used for branding (see [Styling and Branding](#styling-and-branding)).

### System Architecture

The tenant integration has four moving parts:

- the airline frontend page (the host page)
- the Arcube integration script
- the Arcube widget
- the airline basket API

The airline page mounts the widget. The widget sends cart events back to the page, and the airline page updates its own basket.

## Quick Start: Rendering the Widget

Once the airline has authenticated itself and acquired a short-lived widget token (see [Authentication](#authentication-and-token-flow)), the host page can render the widget. The page needs a stable mount element, the Arcube widget bridge script, and a call to `window.Widget.init`.

```html
<div id="arcube-widget"></div>
<script src="PATH_TO_ARCUBE_WIDGET_SCRIPT"></script>
```

Register widget event listeners before initialization when possible, so the parent page can catch early ready, error, and cart events.

```javascript
const widgetConfig = {
  widgetUrl: "ARCUBE_WIDGET_URL",
  tenantId: "YOUR_TENANT_ID",
  sessionId: "YOUR_PNR",            // the booking reference; see note below
  correlationId: "BOOKING_SESSION_ID",
  currency: "USD",
  language: "en-US",
  pointOfSale: "WIDGET",            // selects the payment model - see Payment & Order Creation
  backendUrl: "ARCUBE_BACKEND_URL",
  token: widgetToken,
  themeJsonUrl: "https://cdn.airline.com/arcube/widget-theme.json",
  ancillaryCategories: ["ESIMS", "AIRPORT_TRANSFER"]
};

window.addEventListener("arcube:widget:ready", (event) => {
  console.log("Arcube widget ready", event.detail);
});

window.addEventListener("arcube:widget:error", (event) => {
  console.error("Arcube widget error", event.detail);
});

window.addEventListener("arcube:cart:updated", (event) => {
  const { cart, correlationId, messageType } = event.detail;
  console.log("Arcube widget cart updated", messageType, correlationId, cart);
});

window.addEventListener("arcube:widget:closed", (event) => {
  console.log("Arcube widget closed", event.detail);
});

window.Widget.init(widgetConfig);
```

<Callout type="info" title="sessionId carries the booking reference">
  `sessionId` is the booking the widget operates on. Pass the **PNR** once it exists. If a PNR does not exist yet, a session-level identifier is acceptable for the first step and can be replaced by the PNR later.
</Callout>

The `pointOfSale` value you pass here selects the payment model for the whole session. See [Payment & Order Creation](#payment-and-order-creation) for the full behaviour of each.

## Configuration Reference

All options passed to `window.Widget.init`:

| Option | Required | Description |
|--------|----------|-------------|
| `widgetUrl` | Yes | The Arcube widget URL provided to you. |
| `backendUrl` | Yes | The Arcube backend base URL used for widget API calls. |
| `tenantId` | Yes | Your Arcube tenant identifier. |
| `token` | Yes | The short-lived widget token from the [token flow](#authentication-and-token-flow). |
| `sessionId` | Yes | The booking reference the widget operates on - the PNR, or a session-level identifier before the PNR exists. |
| `pointOfSale` | Yes | Selects the payment model: `WIDGET` (widget owns checkout, Arcube is MoR) or `AIRLINE_WEBSITE` (airline owns checkout, airline is MoR). See [Payment & Order Creation](#payment-and-order-creation). |
| `currency` | Yes | ISO 4217 currency code, for example `USD`. |
| `correlationId` | No | Ties multiple widget invocations for one shopper into a single order and enables [cart persistence](#cart-persistence). If omitted, the Arcube backend generates one, but separate invocations then cannot be tied together into one order. |
| `language` | No | BCP-47 language tag, for example `en-US`. |
| `ancillaryCategories` | No | Restricts which categories render. Omit to render every category enabled for your tenant. Accepted values: `ESIMS`, `BAGGAGE_PROTECTION`, `AIRPORT_TRANSFER`, `FAST_TRACK`, `CARBON_OFFSET`, `LOUNGE_ACCESS`, `CAR_RENTAL`. |
| `themeJsonUrl` | No | HTTPS URL to a hosted theme JSON file for branding. See [Styling and Branding](#styling-and-branding). |

<Callout type="info" title="correlationId and orders">
  `correlationId` is optional. If you do not provide one, the Arcube backend creates it for you - but without a stable value you own, you cannot tie multiple widget invocations (for example after a page refresh, or across steps of the journey) into a single order, and cart recovery after refresh is not guaranteed. When you need that continuity, generate a stable `correlationId` per booking session, store it, and reuse it. Do not generate a new value on every page load.
</Callout>

## Authentication and Token Flow

Before initializing the widget, the airline host page must obtain a short-lived widget token from the Arcube edge endpoint. Arcube uses the tenant ID, requesting origin and PNR to validate the request and issue a token for that booking session.

### Token Endpoints

| Environment | Endpoint |
|---|---|
| Development | `https://dev-edge.arcube.io/token` |
| QA | `https://qa-edge.arcube.io/token` |
| Production | `https://edge.arcube.io/token` |

### Request

Send a `POST` request with:

- `X-Tenant-ID`: the Arcube tenant ID provided to the airline
- `Content-Type: application/json`
- `pnr`: the booking PNR (six-character alphanumeric) in the request body

The request must come from an origin that has been allow-listed for the tenant.

```bash
curl -X POST https://edge.arcube.io/token \
  -H "X-Tenant-ID: YOUR_TENANT_ID" \
  -H "Origin: http://localhost:5173" \
  -H "Content-Type: application/json" \
  -d '{"pnr":"ABC123"}'
```

<Callout type="info" title="Origin header">
  Browsers add the `Origin` header automatically. It should only be added manually when testing with curl or Postman.
</Callout>

Origin matching is exact. The scheme and subdomain are significant, so the following are treated as separate origins:

- `https://example.com`
- `https://www.example.com`
- `https://booking.example.com`

Contact Arcube to allow-list every production origin where the widget will be embedded.

### Response

```json
{
  "accessToken": "<widget-token>",
  "expiresIn": "1h"
}
```

The token is valid for 60 minutes and is scoped to the tenant and PNR provided in the request. Reuse it for the current widget session rather than requesting a new token for every action.

Pass the returned token when initializing the widget:

```javascript
window.Widget.init({
  // ...other configuration
  token: accessToken
});
```

The PNR used by subsequent widget requests must match the PNR associated with the token.

### PNR Feed to Arcube

Before the widget is rendered, the airline must send the PNR feed to Arcube once the PNR and passenger or segment context is available. This lets Arcube store the booking context and prepare personalized recommendations for the widget.

Use the [Ingest Passenger Data](https://docs.arcube.com/docs/reference/essential-api-calls#61-ingest-passenger-data) call. Send the PNR feed to `POST ${arcube-url}/aggregation-api/servePassengerRecommendations` with `pointOfSale: API`. This tells Arcube to store the PNR, passenger, and trip details only; it will not return widget recommendations from this ingest call.

For the first call for a PNR, send `pnr`, `pointOfSale: API`, `passengers`, and `segments`. For later updates to the same PNR, send only the fields that changed.

## Integration Flow

At runtime the integration follows a single linear path:

1. **Render** - the host page mounts the widget when the user reaches the step where extras are offered. Mount when that view is active and destroy it when the view unmounts.
2. **Search** - the widget uses the session and flight context from the host page. For some ancillaries the passenger enters extra product-specific details, such as pickup and drop-off addresses or driver age.
3. **Select** - the passenger selects an ancillary product without leaving the host page.
4. **Add to cart** - when the passenger adds an item, the widget emits a cart event to the parent page. The host page receives it and updates its own basket (see [Handling Cart Events](#handling-cart-events)).
5. **Checkout** - the normal flow continues. Payment is completed inside the widget or by the airline, depending on the [payment model](#payment-and-order-creation).

## Tenant Event Contract

The widget and the parent page exchange messages to keep the widget UI and the airline basket in sync. Some messages are sent by the widget to the parent page (for example when an item is added or removed); others are sent by the parent page to the widget (for example when the airline basket changes outside the widget).

| Event / Command | Direction | Meaning | Integration handling |
|---|---|---|---|
| `arcube:widget:ready` | Widget → Parent | Widget is ready | Mark the widget area as live |
| `arcube:widget:error` | Widget → Parent | Widget failed | Show fallback UI and log the error |
| `arcube:widget:closed` | Widget → Parent | Widget closed itself, for example when no ancillaries are available | Optional: hide surrounding chrome such as section headings |
| `arcube:widget:resize` | Widget → Parent | Widget content height changed | Optional: resize the iframe/container and apply any parent-side max height |
| `arcube:cart:updated` + `CART_ITEM_ADDED` | Widget → Parent | User added an item in the widget | Add the item to the airline basket |
| `arcube:cart:updated` + `CART_ITEM_REMOVED` | Widget → Parent | User removed an item in the widget | Remove the item from the airline basket |
| `CART_ITEM_REMOVE_REQUEST` | Parent → Widget | Parent asks the widget to remove one selected item | Use when one item is removed from the airline basket outside the widget |
| `CART_CLEAR_REQUEST` | Parent → Widget | Parent asks the widget to clear all selected items | Use when the airline basket is cleared outside the widget |

## Handling Cart Events

The widget does not write into the airline basket directly. It emits cart events. The airline frontend must listen to those events and run its own add-to-cart logic. Each widget event contains a cart snapshot with the root `customer` and a flat `selectedAncillaries` array.

### Catching the Add Event

Listen for cart update events and extract the latest selected ancillary from the cart:

```typescript
function getLatestSelectedAncillary(detail: ArcubeCartUpdateEvent) {
  const items = detail.cart.selectedAncillaries;
  return items[items.length - 1] ?? null;
}

window.addEventListener("arcube:cart:updated", (event) => {
  const detail = (event as CustomEvent<ArcubeCartUpdateEvent>).detail;
  if (!detail || detail.messageType !== "CART_ITEM_ADDED") return;

  const latest = getLatestSelectedAncillary(detail);

  if (!latest) return;

  console.log("Widget item added", latest);
  // Pass latest into your own add-to-cart flow.
});
```

### Sending Updates to the Widget

The airline can also send data and commands to the widget - for example when the airline basket changes outside the widget. Runtime communication happens by posting a browser message to the embedded widget window.

```javascript
const widgetUrl = "use the same widget URL configured in your integration";
const widgetOrigin = new URL(widgetUrl).origin;

function getEmbeddedWidgetWindow() {
  const frame = document.querySelector("#arcube-widget-container iframe");
  return frame?.contentWindow ?? null;
}

function sendToWidget(message) {
  const widgetWindow = getEmbeddedWidgetWindow();
  if (!widgetWindow) return;

  widgetWindow.postMessage(
    {
      source: "arcube-parent",
      version: "1.0",
      timestamp: new Date().toISOString(),
      ...message
    },
    widgetOrigin
  );
}

function removeItemFromWidget(itemId) {
  sendToWidget({
    type: "CART_ITEM_REMOVE_REQUEST",
    payload: { itemId }
  });
}

async function handleRemove(itemId) {
  await removeFromAirlineCart(itemId);
  removeItemFromWidget(itemId);
}

function clearWidgetCart() {
  sendToWidget({
    type: "CART_CLEAR_REQUEST",
    payload: {}
  });
}

async function handleClearCart() {
  await clearAirlineCart();
  clearWidgetCart();
}
```

The parent page can pass passenger details to the widget so customer and passenger forms are prefilled. Send the data after the widget emits `arcube:widget:ready`, and send it again if the booking passenger data changes.


All fields in the `customer` object are required. The `countryCode` must be provided as an international calling code, such as `+234`. The widget validates and formats the phone number using the supplied country code and returns the result in `isValid`. A valid phone number is required before Airport Transfer or Car Rental products can be added to the cart, as their providers require verified customer contact details to process the booking reliably.

`customer` is used for the primary customer details form. `passengers` is used to prefill additional passenger forms for products that require traveler-level information. Mark the primary traveler with `isPrimary: true`.

### Cart Persistence

Cart persistence allows the widget to restore a shopper's selected ancillaries if they refresh the page or return shortly after. The airline only needs to pass a stable `correlationId` when initializing the widget.

```js
window.Widget.init({
  correlationId: "BOOKING_SESSION_ID",
  tenantId: "...",
  sessionId: "...",
  // ...rest of your config
});
```

The `correlationId` must be unique to one shopper / booking session, and the airline should store it. Reuse the same value every time the widget is loaded for that booking, including after a refresh. Do not generate a new `correlationId` on every page load - if the value changes, the widget treats it as a different cart and cannot recover the previous selections.

If no `correlationId` is provided, the widget still works and the backend generates one, but cart recovery after refresh is not guaranteed and separate invocations cannot be tied into one order. Persisted carts expire automatically after the backend retention window, currently about 2 hours.

When a saved cart is restored, the widget emits the normal cart update event, so the parent page can keep its cart badge, summary, or booking UI in sync using the existing `arcube:cart:updated` listener.

### Automatic Close When No Ancillaries Are Available

If the recommendations API returns no sellable ancillaries for the current session, the widget closes itself: the integration script removes the iframe and hides the host mount node (`#arcube-widget`) so no empty slot remains in the page. It also dispatches `arcube:widget:closed` so the tenant can react - for example, by hiding a surrounding "Extras" section heading.

```javascript
window.addEventListener("arcube:widget:closed", (event) => {
  const { reason, correlationId } = event.detail;
  // reason is "no_ancillaries" when the widget closed because the
  // recommendations response was empty.
  console.log("Arcube widget closed", reason, correlationId);
});
```

The next call to `window.Widget.init(...)` restores the mount node and remounts the iframe, so this behavior is fully reversible.

### Optional Iframe Height Control

The widget emits its current content height through the `arcube:widget:resize` event whenever the widget layout changes. The parent page can listen and resize the iframe. If the airline wants to cap how tall the widget can become, the max height should be handled in the parent page.

```javascript
const widgetMaxHeight = 900; // Set to undefined to allow full content height.

function resizeArcubeWidgetFrame(height) {
  const appliedHeight = widgetMaxHeight ? Math.min(height, widgetMaxHeight) : height;
  const nextHeight = `${appliedHeight}px`;
  const mount = document.getElementById("arcube-widget");
  const container = document.getElementById("arcube-widget-container");
  const iframe = container?.querySelector("iframe");

  [mount, container, iframe].forEach((element) => {
    if (!element) return;
    element.style.setProperty("height", nextHeight, "important");
    element.style.setProperty("min-height", nextHeight, "important");
    element.style.overflow = "visible";
  });
}

window.addEventListener("arcube:widget:resize", (event) => {
  resizeArcubeWidgetFrame(event.detail.height);
});
```

When `widgetMaxHeight` is set, the iframe grows until that value and then stops. If the widget content later becomes smaller, the iframe shrinks again to the new content height.

## Payment and Order Creation

The payment model is selected by the `pointOfSale` value you pass to `window.Widget.init`. It determines who captures payment, who is Merchant of Record, and whether the airline needs to create the order itself.

| | Model A - Widget-owned | Model B - Airline-owned |
|---|---|---|
| `pointOfSale` | `WIDGET` | `AIRLINE_WEBSITE` |
| Who captures payment | The widget, inside its own frame | The airline, on its own PSP |
| Merchant of Record | Arcube | Airline |
| Airline order-create call | Not required | Required (`widget-order-create` with `externalPSP`) |
| Best for | Standalone pages, manage-my-booking, lighter integrations | Deep booking-flow integration with a unified basket |

### Price Verification

Before creating an order, a tenant may optionally perform a Price Verify call to validate the prices being submitted and determine the required payment split for third-party ancillaries. The endpoint serves two purposes:

- **Price validation** - verifies that the prices submitted by the tenant match the prices calculated by Arcube.
- **Payment split calculation** - returns the amounts that must be captured on behalf of the airline and on behalf of Arcube.

More information is available under [Reference → Essential API Calls → Verify Prices](/docs/reference/essential-api-calls#63-verify-prices).

<Callout type="info" title="When Price Verify is needed">
  Price Verification is optional when the payment flow does not involve Split Payments. Arcube already has full visibility of the priced ancillaries through its pricing engine, so an additional price verification step is not required in standard non-split-payment flows.

  The Price Verify call should be executed before payment capture by the Merchant of Record. This ensures the correct capture amount is calculated and allocated for each Merchant of Record in the transaction. In Model B, the Arcube-side amount from this split is what you report as `externalPSP.amount` when creating the order.
</Callout>

### Model A - Widget-owned checkout (`pointOfSale: WIDGET`)

When the widget is rendered with `pointOfSale: WIDGET`, the widget owns the ancillary checkout and captures payment **inside its own frame**. **Arcube is the Merchant of Record.** The airline embeds the widget and listens for cart events; it does not run a checkout and does not call the order API itself - the widget completes payment and creates the order with Arcube directly.

Use this model for standalone pages, manage-my-booking, and lighter integrations where Arcube handles payment and settlement. The parent page still receives `arcube:cart:updated` events and can keep its own cart badge or summary in sync, but no airline-side order-create call is required.

### Model B - Airline-owned checkout (`pointOfSale: AIRLINE_WEBSITE`)

When the widget is rendered with `pointOfSale: AIRLINE_WEBSITE`, the airline owns checkout and captures payment on its own PSP. **The airline is the Merchant of Record.** After capturing payment, the airline creates the order through `/transactions/widget-order-create`, passing proof of the charge in an `externalPSP` object. Arcube never collects payment in this model - it places the ancillary orders with the relevant providers and records the transaction.

Immediately before charging the customer and creating the order, call [Verify Prices](/docs/reference/essential-api-calls#63-verify-prices) to confirm that the cart prices still match Arcube's authoritative bundle. Re-confirm with the user if any item has drifted.

When sending the order payload, put the primary passenger/customer in `customer`. The `passengers` array should include only additional passengers and should exclude the primary passenger.

#### Payment Proof (`externalPSP`)

To create the order, the airline must pass back proof of the charge it already captured in an `externalPSP` object. The amount to report is the **Arcube-side capture** - the portion of the total captured on behalf of Arcube, as returned by the payment split in [Verify Prices](/docs/reference/essential-api-calls#63-verify-prices).

<Callout type="warn" title="externalPSP is required in Model B">
  When the airline is Merchant of Record, the order request is rejected with `400 MISSING_EXTERNAL_PSP` if `externalPSP` is absent or any required field is invalid. The response `details` array lists each offending field.
</Callout>

| Field | Required | Description |
|-------|----------|-------------|
| `provider` | Yes | The airline's PSP, e.g. `"stripe"`, `"adyen"`. |
| `referenceId` | Yes | The PSP charge/transaction id. Arcube indexes the transaction by this value. |
| `status` | Yes | Payment status. Use `"CONFIRMED"` for a successful charge. See the allowed values below. |
| `amount` | Yes | Captured amount as a positive number (the Arcube-side share). |
| `currency` | Yes | ISO 4217 currency code, e.g. `"USD"`. |
| `paidAt` | Yes | ISO 8601 timestamp of when the charge was captured. |
| `paymentMethod` | No | Display metadata, e.g. `"card"`. |
| `cardType` | No | Display metadata, e.g. `"visa"`. |
| `cardLastFour` | No | Display metadata, e.g. `"4242"`. |
| `rawPayload` | No | Raw PSP response, stored as-is for reconciliation. |

Allowed `status` values:

| Status | Meaning | When to send |
|--------|---------|--------------|
| `CONFIRMED` | Payment successfully captured. | The standard case for order creation - the airline has already captured payment for the ancillaries before calling this endpoint. |
| `PENDING` | Payment initiated, awaiting the final result. | The charge is still being processed asynchronously (e.g. awaiting 3-D Secure or an async PSP confirmation) at order-create time. |
| `FAILED` | Payment was declined or failed. | Reported for reconciliation when a charge attempt did not succeed. |
| `CANCELLED` | Authorization voided / payment cancelled before capture. | The reserved authorization was released and no funds were captured. |
| `PARTIALLY_REFUNDED` | Part of the captured amount has been refunded. | Reported when part of an earlier charge is later refunded. |
| `REFUNDED` | The full captured amount has been refunded. | Reported when an earlier charge is later refunded in full. |

<Callout type="info" title="Request URL Parameter">
  Replace `${arcube-url}` with your assigned Arcube environment URL (e.g., `https://api.arcube.com`).
</Callout>

<Callout type="info" title="HTTP Method: POST">
  **URL:** `${arcube-url}/transactions/widget-order-create`
</Callout>

<Callout title="Request Headers">

## Styling and Branding

The widget can be branded to match the airline experience. The current styling contract is based on a hosted theme file. The airline hosts a theme JSON file on a publicly accessible HTTPS URL and passes that URL to the widget as `themeJsonUrl` when the widget is opened. The hosting bucket or CDN must allow public GET requests with CORS enabled so the widget can fetch the file from the browser.

The widget reads that theme file, applies the color and typography tokens internally, and keeps the styling scoped to the widget itself. If the airline wants a custom font, the theme file can include a `font-url` value - an HTTPS stylesheet link such as a hosted font stylesheet or a Google Fonts URL. The widget loads that stylesheet automatically and uses the declared `font-family`.

The theme file should include an `en` block with a colors section and a typography section. At minimum, the widget expects:

- `primary`, `secondary`, `bodyBg`, `neutral`, `black`, `white`, `link`
- `typography.font-family`

Optional color values - `success`, `warning`, `danger`, and `info` - may also be provided.

When opening the widget, pass a `themeJsonUrl` pointing to the hosted theme file:

```
themeJsonUrl=https://cdn.airline.com/arcube/widget-theme.json
```

**Example theme file:**

```json
{
  "en": {
    "colors": {
      "primary": "#12ADEF",
      "secondary": "#0A3D62",
      "bodyBg": "#F7FAFC",
      "neutral": "#C8D2DC",
      "black": "#111111",
      "white": "#FFFFFF",
      "link": "#12ADEF",
      "success": "#2E9E5B",
      "warning": "#E8B949",
      "danger": "#D75656",
      "info": "#4AA3C7"
    },
    "typography": {
      "font-family": "Airline Sans, Arial, sans-serif",
      "font-url": "https://cdn.airline.com/fonts/airline-fonts.css"
    }
  }
}
```

If the theme file cannot be fetched, is invalid, or is missing required values, the widget falls back to the default Arcube styling. For that reason, host the theme file on a stable HTTPS URL and treat it as part of the production integration.

## Error Handling

The widget must never block the airline booking flow. Follow these rules to handle errors:

- If the widget is not available, hide the widget area
- If the widget emits an `arcube:widget:error` event, log it and keep the airline flow usable
- If your cart update fails, show a clear message and do not assume the ancillary was saved
- If session data is missing, do not mount the widget

Listen for error events and wrap your cart update logic in a try-catch block:

```typescript
window.addEventListener("arcube:widget:error", (event) => {
  const detail = (event as CustomEvent<{ code: string; message: string }>).detail;
  console.error("Arcube widget error", detail);
  // Hide the widget area or show fallback UI here.
});

async function handleCartAdd(runCartLogic: () => Promise<void>) {
  try {
    await runCartLogic();
  } catch (error) {
    console.error("Cart update failed", error);
    // Show a clear message to the user here.
  }
}
```
